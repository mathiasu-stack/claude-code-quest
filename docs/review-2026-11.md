# Claude Code Quest — independent review, November 2026

Reviewer: Claude Code (Opus 5.5), read-only review, 2026-11-24.
Scope: the repo at `HEAD = 4e123ad` (2026-08-30) plus the uncommitted `RESUME.md` notes. I ran the
audit suite and checked the live public deployment, using HTTP status codes only.

> **Handling note.** This file lives inside the directory that `save_server.py` serves to the
> internet. The security findings below therefore describe each problem by class. They contain no
> working request paths, passcodes or keys. Keep it that way until item R0 of the roadmap ships.

---

## 1. Executive summary

The teaching core works, and it is reasonably well engineered for a zero-dependency project: one
progress model is shared by both UIs, the audits are green, and the offline build is careful. Four
things undercut it, though. **(a) The public deployment is exposing secrets right now.** The
server's blocklist can be bypassed, which exposes the Azure TTS key file, the whole `.git`
directory, the error log with player IPs, and the server source that contains the admin passcode.
That passcode also gates a *write* endpoint whose output is served to every player as `<script>`.
**(b) The content is one model generation behind again.** The 5.5 family shipped, and Claude Code
now defaults to Opus 5.5 at `medium` effort. Several lessons were wrong from the start (how hooks
block, how the status line gets its input, a headless script that can't write its own output), and
the quizzes grade those wrong answers as correct. **(c) Every practical test can be passed with a
38–159-character keyword list** (17/17), so the tests check vocabulary, not skill. **(d) The 3D
layer is at capacity.** The 4×4 floor grid is full, ch16's lesson-7 NPC (added in the last commit)
spawns outside the floor-4 wall and can't be reached, and `play.js` is 7,808 lines (not the ~3,900
in the brief).

**Overall verdict: Targeted refactor.** That means an urgent security hotfix, then a content pass
that moves volatile facts into data, then evaluator hardening, then splitting the 3D layout away
from array position. Nothing here justifies a rebuild.

## 3. Findings by dimension (ranked by severity within each)

### 5. Public exposure (listed first because it is the only urgent item)

The deployment is Tailscale Funnel → `http://127.0.0.1:8888` → `save_server.py`, confirmed with
`tailscale funnel status`. nginx is DSM's own and **not** in the path, so `save_server.py` is the
whole security boundary.

**MUST FIX — S1. Path blocklist is bypassable; secrets are publicly downloadable.**
`save_server.py:141-156`: `do_GET` compares the *raw, un-normalized* request path against
`_BLOCKED_PREFIXES` with `startswith`. `SimpleHTTPRequestHandler.translate_path` later
percent-decodes and normalizes dot-segments, so equivalent spellings of a blocked path slip past
the check and are served. I verified this **through the public Funnel hostname**. Each of these
returned 200 with a non-empty body:
- `tts_config.json`: the Azure Speech key (148 bytes),
- `.git/` (config confirmed, so the whole repo and its history can be dumped),
- `logs/errlog.jsonl` (76 KB, with player IPs and user agents: `save_server.py:243`),
- `save_server.py` (contains the plaintext admin passcode, `save_server.py:51`),
- `RESUME.md`, `scripts/`, `tts-cache/`.

Also: `do_HEAD` (`:158`) applies no blocklist at all. Separately, some paths are not on the list in
the first place and are plainly served: `.claude/`, `design/`, `NIGHT_RUN_NOTES*.md`,
`CURRICULUM.md`, `test-poses.html`, and **directory listings** of
`play/assets/characters/_originals/` and `Blender/` (~900 MB of raw GLBs on disk; a bandwidth sink).
*Consequence:* the Azure key should be treated as compromised and rotated.

**MUST FIX — S2. The "cosmetic" admin gate protects a server-side write that becomes stored XSS.**
The brief accepts the admin gate as cosmetic, and that holds for the client-side unlock. It does
not hold here, because the same passcode authorizes `POST /save` (`save_server.py:184-219`). That
endpoint overwrites `data/rooms.js`, `npc_overrides.js`, `lesson_delivery_overrides.js` and
`compound_overrides.js`, and `index.html:72-87` loads all four into **every** player's page via
`document.write('<script src=…>')`. The passcode can be obtained without guessing. It is in
plaintext in `save_server.py`, which is readable via S1, and it also ships inside the public
offline zip (`downloads/claude-code-quest-offline.zip` → `claude-code-quest/save_server.py`,
verified). The client hash in `app.js:616` is unsalted SHA-256 of a 7-character word, so it is
weak as well. Anyone on the internet can therefore make the hosted game run arbitrary JS for every
visitor. CORS is also `*` on POST (`:107`).

**MUST FIX — S3. `/tts` is an open, unauthenticated proxy to a paid Azure API.**
`save_server.py:268-330` accepts any text (≤800 chars) with any matching voice name, synthesizes
it on your key, and caches it to disk **with no size cap**. There is no rate limit, auth or origin
check. Each unique string is a billed call plus a new file on the NAS volume.

**SHOULD — S4. `/errlog` is an open append log** (`:226-256`). Anyone can fill it to the 5 MB cap,
after which real errors are silently dropped (`'note': 'log full'`). It stores IPs, which is
personal data now that the audience is public; decide on retention.

**NICE — S5.** `save.php` duplicates the passcode (`save.php:24`) and is dead on this deployment;
delete it or keep it out of the served tree.

**What a fix looks like (cost S, no new dependencies):** replace the blocklist with an
**allowlist**: resolve `translate_path()` → `realpath`, then serve only if it sits under an
explicit set of shipped roots (`index.html`, `style.css`, `app.js`, `engine/`, `ui/`, `data/`,
`play/` minus `_originals`/`Blender`, `downloads/`). Deny dot-segments and dotfiles. Disable
directory listing (override `list_directory`). Turn `/save` off on the Funnel-facing listener; the
simplest way is a second process bound to the tailnet IP only for the editor. Restrict `/tts` to
lines that exist in the shipped dialogue data (hash allowlist built from `data/story_*.js`) or to
cache hits only. Rotate the Azure key and the passcode, and take the passcode out of the zip.

### 1. Content freshness

Verified 2026-11-24 against the live docs listed in §4 (Claude Code docs at code.claude.com,
model and pricing pages at platform.claude.com). `lastVerified` stamps confirm the drift: 28 of 71
lessons were last verified 2026-04-22, and none after 2026-08-26.

**MUST FIX — C1. The model generation is stale, and quizzes grade the now-wrong answer as correct.**
Current models are Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.2. **Claude Code defaults to
Opus 5.5 on every plan, and the 5.5 models default to `medium` effort.** The curriculum teaches
Opus 5 / Sonnet 5 (default) / Haiku 4.5 / Fable 5, and says `high` is the default effort:
`ch10-q01` keys "Sonnet 5", and `ch10-q13` keys "high". The **cost lesson is inverted**:
Haiku 5.5 starts at $0.10/$0.50 and has 1M context, so Opus 5.5 ($4/$20) is roughly **40×** Haiku,
not 5×, and "Haiku stays at 200k" is false (`ch07-l01`, `ch07-q01`, `ch10-l01..l03`).

**MUST FIX — C2. Lessons that were wrong from the start (not drift):**
- `ch15-l03` and `ch15-mcq`: "PreToolUse… can block by exiting non-zero". In fact **only exit 2
  blocks**; exit 1 is a non-blocking error and the tool call proceeds. Taught as-is, this is a
  security-relevant mistake: a learner's "block prod DB" hook would silently not block.
- `ch15-l04`: the status line script gets data "via environment variables". In fact it gets
  **JSON on stdin**.
- `ch16-l06` (and `ch16-mcq`): the scheduled job says "Save the draft to reports/draft.md" but runs
  `--permission-mode plan`, which **blocks edits**. The flagship automation recipe can't produce
  its own output.
- `ch08-test`: asks for `.claude/skills/support-reply.md`. Skills must be
  `.claude/skills/<name>/SKILL.md`; a loose `.md` belongs in `.claude/commands/`.
- `ch13-l04`: `new Server(...)` then `server.tool(...)`. The documented high-level API is
  `McpServer` + `registerTool` (and the SDK main line is now v2 with new package names).
- `ch03-mcq`: "200k; 1M on Max, Team, and Enterprise". In fact 1M is the default on every current
  model; plan gating applies only to legacy Opus 4.6 / Sonnet 4.6.
- `ch01-l03` and `ch01-mcq`: use `/compact` before exiting so you can resume; "sessions do not
  persist on their own". In fact sessions persist, and `claude --continue` / `--resume` / `/resume`
  are the mechanism. **Resume is taught nowhere** (0 hits for `--continue|--resume|/resume`).

**SHOULD — C3. Reversals of the August pass.** `ch15-l04` says "There is no /output-style
command… removed in v2.1.91", and `ch11-l01` repeats it. `/output-style [style]` is back in the
commands table (v2.1.269+).

**SHOULD — C4. Prompt-cache TTL is taught as a hard 5 minutes** in 6 places (`ch07-l01`,
`ch10-l03`, `ch16-l06`, `ch07-mcq`, `ch10-mcq`, `ch16-mcq`), and `ch10-test` rewards the keyword
"5 minute". On a subscription within plan usage, the main conversation now gets a **1-hour** TTL by
default, configurable with `promptCacheTtl`. Cache reads on Opus/Sonnet 5.5 are 0.05×, not "~10%".

**SHOULD — C5. Important current features with zero coverage** (0 grep hits each): `--continue`
/ `--resume` / `/resume`, `/rewind` (checkpoints), worktrees, `/loop`, `/schedule` (routines),
`/goal`, `/tasks` / background sessions, `/diff`, `/code-review` (it is mentioned only as
`/review`; the `--fix`, `--comment` and `ultra` modes are not taught), `/btw`, `/context`,
`/import`, `/powerup`, managed settings, and the `onFailure` hook option.

**Structural observation.** Model names, prices, defaults and TTLs are spread across prose in
~20 lessons and ~15 quiz items. Every model release forces another hand sweep, and this is the
third (`RESUME.md`: passes ②, ③). The fix is a single `data/facts.js` that lessons interpolate
(see roadmap R3).

### 2. Completeness

**Audit output** (`bash scripts/audit/run-all.sh`, verbatim summary):
```
=== DATA CONSISTENCY ===  12/12 PASS (94 NPCs, 17 chapters, 71 lessons, 113 criteria)
=== SPATIAL ===           5 PASS, 2 NOTE (interior walls + play.js placements not audited)
=== SMOKE ===             3/3 PASS (98 .js parse, 23 script refs, 15 GLBs on disk)
AUDIT: all clean.
```
The audits are green, but they miss the two worst completeness bugs below, which shows where their
blind spots are: bounds, and grading strength.

**MUST FIX — P1. ch16-l07 is unreachable in 3D, so the ch16 assessor is gated forever in 3D.**
`play.js:3512-3543` places floor-2–4 lesson NPCs at `slot.cx + (lessonIdx-1)*1.4`. ch16 is index
15, i.e. floor 4, slot 3, `cx = +13`. Its NPCs land at x = 17.2 (l05), **18.6 (l06, inside the
wall at 18)** and **20.0 (l07, outside the 36 m floor)**. The player is clamped to |x| ≤ 17.5
(`play.js:748`) and interaction needs < 2.4 m (`play.js:~6936`), so l07 can't be reached.
`computeAheadGate` (`play.js:5290`) then makes the ch16 assessor defer until l07 is done.
ch16-l07 was added in the last content commit (`eb93504`). The dashboard path still works, so this
blocks 3D players, not the course. *Unverified in a browser* (there is no browser automation
here); it can be confirmed by walking to floor 4's south-east room.

**MUST FIX — P2. All 17 practical tests pass with keyword salad.** I built each submission from
the first keyword of every criterion, plus the nonce and a 3-line numbered list where a
`structure` criterion exists. All **17/17 scored 100**, using 38–159 characters
(`engine/evaluator.js:4-6`: a `keyword` criterion passes on *any* substring hit; most tests have
`minLength: 0`). The nonce only proves the learner had the test page open, because it is shown on
screen. The certificate-like "promotion" therefore attests to vocabulary, not practice. Whether
that matters is a product decision (see open questions), but it should be a deliberate one.

**SHOULD — P3.** All 71 lessons render the "Video lesson coming soon" placeholder
(`ui/lesson.js:34`). Either produce videos or remove the placeholder; a permanent "coming soon" on
every page reads as unfinished.

**SHOULD — P4. Audit blind spots that let P1 and P2 ship:** no NPC-within-floor-bounds check, no
"interactable from the walkable area" check, no evaluator-strength check, and the module-fork
check described in A3. All of them are cheap static checks.

**Fine:** the 2D dashboard and 3D view share one progress object (`window.App.progress` →
`engine/progress.js`), so they cannot disagree on lessons, tests or unlocks. The one duplication is
the floor math (A2).

### 3. Architecture and maintainability

**SHOULD — A1. `play.js` is a 7,808-line god module.** It has 69 imports, ~72 module-level
`let`/`var` bindings, and a single `update(dt)` of ~650 lines (`play.js:6349-7005`). The natural
seams are already visible in the function list:

| Proposed module | Current range (approx.) | Contents |
|---|---|---|
| `npc/roster.js` | 91-600, 4575-4780 | `NPCS`, people pool, `generateChapterNPCs`, `spawnNPC`, overrides |
| `world/layout.js` | 255-420, 3468-3545 | floor/zone/slot math, `floorFor*`, zone boxes |
| `world/furniture.js` | 1118-1580 | `buildDesk/Chair/Lamp/…` (pure builders, easiest to extract) |
| `world/floors.js` | 2850-3460, 3945-4135, 4782-4840 | `buildWorld`, `buildFloorOffice`, `loadFloor` |
| `story/ceo.js` | 1582-2050, 5447-5535 | Maya portrait, finale chain, epilogue |
| `dialogue/dialogue.js` | 5146-5450, 5552-6010 | intro, gating, story overrides, typewriter |
| `objective.js` | 6169-6310 | objective ring and compass |
| `core/loop.js` | 4870-4900, 6349-7130 | renderer, `update`, loop, frame telemetry |
| `player.js` | 4135-4452 | player rig and accessories |

Extract the pure builders first (zero shared state), then layout math (it is already a near-pure
function of `CURRICULUM`), then the roster. Leave `update()` until last.

**SHOULD — A2. Fragile invariants.**
- *Index-based floor routing* is implemented **twice**: `play.js:257-281` and
  `engine/progress.js:297-329`, each with its own `CHAPTERS_PER_FLOOR = 4` and `FLOORS_TOTAL = 4`.
  Reordering `CURRICULUM` silently moves NPCs, floors, badge thresholds and `ZONE_THEMES`
  (`play.js:413`). Lesson-slot routing additionally parses the lesson **id suffix**
  (`play.js:3537`), which caused P1.
- `HAND_BUILT_CHAPTER_IDS = new Set(['ch01','ch02'])` (`play.js:4746`) is checked in three places
  (`:4769`, `:5266`, the audit). It is fine as a mechanism, but it should be a data flag
  (`chapter.npcs: 'hand-built'`), not a set in the engine.
- `ZONE_COUNT = 16` and `FLOOR_M_ZONE = 16` (`play.js:292-299`) are coupled to the current chapter
  count; a 17th zone would alias Floor M's lighting and music.

**SHOULD — A3. Module identity forks from `?v=` mismatches**, the same trap `RESUME.md` documents
for `quality.js` and `AudioManager`, and it is live in two more places:
- `play/world/floorM.js:260` imports `decorationAssets.js` **without** `?v=`, while play.js and
  five other importers use `?v=20260528j`. Floor M gets a second module with an empty `_cache`,
  so its decorations always fall back to procedural props (visual only).
- `play/editor/roomsEditor.js:35` imports `interactables.js?v=20260527i`, while 11 object types
  import it bare. The editor's `setAllGlowsVisible` iterates an **empty** `_state.list`, so it is a
  no-op (editor only).

This is the concrete, recurring cost of hand-maintained cache busting (A5).

**Change walk-throughs (as of today):**
- *Add a lesson to an existing chapter.* 1 file (`curriculum*.js`) plus re-running the audit. The
  NPC is auto-generated. Hidden trap: on floors 2–4, lessons 6+ land in or outside the wall (P1),
  and ch02's hand-built roster needs a manual NPC in `play.js`. **1–2 files, 2–3 steps, one
  silent failure mode.**
- *Add a chapter.* Curriculum object (1 file), then a `ZONE_THEMES_BY_ID` entry and optionally a
  lighting preset (`zone-presets.js`), story lines (`story_lines.js`), and an MCQ pool. **But the
  4×4 grid is full**: index 16 lands on floor 4, slot 0, on top of ch13's room (`idx % 4`). So
  adding a main chapter today requires changing the floor model in 2 files (`play.js`,
  `progress.js`) and probably the elevator, badges and story tiers as well. **~6 files, and not
  possible without engine work.**
- *Add a room.* Floor 1: a `data/rooms.js` entry (or the in-game editor) plus a builder `fn` in
  the `registerRoomBuilders` map (`play.js:2414`). Floors 2–4: imperative code in
  `buildFloorOffice`. **1–2 files on floor 1, play.js surgery elsewhere.** Note: the
  "rooms-to-data refactor" in the brief is already **half done**. `rooms.js`,
  `world/roomsLoader.js` and a 2,121-line `editor/roomsEditor.js` exist for floor 1.
- *Add an NPC.* Flavor NPC: append to `NPCS` in `play.js` (+ optional `story_lines.js`). Lesson
  NPC: automatic. **1–2 files.**

**Zero-dependency / no-build: both sides.**
*For keeping it:* the offline zip works because there is no toolchain. Players double-click and it
runs (`HOW TO PLAY OFFLINE.txt`, the PowerShell fallback). The NAS serves straight from disk. There
is no supply chain to audit, and 98 files parse with `node --check`. Nothing is blocked by the
lack of a bundler.
*Against it:* manual `?v=` strings (46 in `play.js`, 69 relative imports) have now forked modules
four times (A3 plus the two in `RESUME.md`). There is no type checking across a ~30k-line
codebase, and the 165 KB / 152 KB curriculum files are hand-edited HTML-in-JS strings with no
lint for broken markup.
*Conclusion:* **keep runtime zero-dependency and no-build.** Fix the real cost in place: move cache
busting into the existing importmap (one version per module, in one place, which makes forks
impossible), and add `// @ts-check` with JSDoc, run by an optional dev-only `tsc --noEmit`. That
removes most of the pain at about 5% of the cost of adopting a bundler, and the offline story is
unchanged.

### 4. Scalability

**SHOULD — L1. Curriculum ×2 (32 chapters / 120 lessons): the 3D layout breaks first.** The
breakages arrive in this order: the 4 floors × 4 slots cap (A2) → per-room lesson capacity of
~4 on floors 2–4 (P1) → `ZONE_COUNT` and the lighting/music zone tables (`zone-presets.js:373`) →
elevator floor list and badge math. The 2D dashboard, progress engine and evaluator scale fine:
they are plain arrays keyed by id. Curriculum source files would pass 300 KB each; split them
per chapter (`data/chapters/chNN.js`).

**SHOULD — L2. Memory: floors are additive.** `loadFloor()` (`play.js:4796`) builds a floor once
and afterwards only toggles visibility; nothing is disposed (18 `dispose` calls in play.js, none
on floor exit). A full playthrough keeps all 5 floors' geometry, NPC rigs and textures resident.
That is acceptable at 4 floors with the graphics tier, but it is the first thing to break on
mobile Safari as floors grow. Fix: dispose floors that are not adjacent to the current one, and
keep the GLB cache (that part is already shared).

**SHOULD — L3. Data model readiness:**
- *Multiple courses:* not ready. `window.CURRICULUM` is a single global array, progress is keyed
  by globally unique lesson ids with no course namespace, and the key is a single `ccq_progress`.
- *Languages:* not ready. All copy is English HTML inside JS strings, `<html lang="en">`, and
  there is no string table. TTS voices are already per-locale names, which is the one piece that
  would carry over.
- *Multiple users:* single-player by design (`localStorage`). Export/import exists
  (`progress.js:372-396`). Fine for a self-serve course; not for anything that reports completion
  to an employer.

### 6. Relevance: stepping back

**The dashboard and lesson HTML do the teaching.** In 3D, a lesson NPC opens the same `content`
HTML in an overlay (`play/lessons/overlay.js`), and tests are the same `ui/test.js`. Every learning
outcome is reachable without the 3D view. The 3D office contributes motivation (story arc,
ceremonies, the Maya finale), wayfinding and novelty. Engineering-wise it costs about 85% of the
non-vendored JS, all of the asset pipeline, and every bug in §2 except P2.

My candid read: the 3D layer is **earning its keep as engagement** only if people actually play
it. The memory file still lists "playtest" as the #1 gap, so there is no evidence either way. That
is the cheapest open question to resolve (see open questions). Do not cut it on my say-so, and do
not grow it (more floors, rooms or NPCs) until that evidence exists.

**What a learner in late 2026 expects and does not get:**
1. **Practice verified against real Claude Code**, not self-reported text (P2). Claude Code now
   ships its own interactive lessons (`/powerup`), so a third-party course has to offer something
   the product doesn't: realistic scenarios and verified outcomes.
2. **The current daily workflow:** resume/rewind, `/diff` → `/code-review` → ship, worktrees and
   background tasks, `/loop`, `/schedule` and `/goal` (C5). The curriculum is strong on
   configuration (CLAUDE.md, skills, hooks, settings) and thin on the delegate → verify → ship
   loop that is now the core skill.
3. **Freshness signals:** visible "verified against vX on date" per lesson. The data already
   exists (`lastVerified`), but it isn't shown to learners.

**Where the planned rooms-to-data refactor and room editor fit.** The refactor is half done:
floor 1 runs on `rooms.js`, `roomsLoader.js` and the editor. **Change the plan.** Don't extend
per-object hand placement to floors 2–4. Make those floors **templated from data** (R6: a floor
template plus N chapter slots generated from the curriculum), and keep the editor for floor 1's
bespoke spaces and for overrides. Hand-placing rooms is what doesn't scale to 32 chapters. The
editor must not be reachable from the public listener (R0), because its save path is the stored-XSS
vector.

**Explicitly not recommended:** a rebuild, a framework, or a bundler. *Cost* of a rebuild: months
of re-creating the 3D content, story and offline packaging, with a high risk of regressing a
working game. *Do-nothing alternative:* it keeps working for current content, but R0 is not
optional, and each model release will cost another manual sweep. *Incremental (R0–R9)* fixes
every must-fix in roughly S+S+M+M and leaves the larger structural work to be paced by real usage.

## 6. Open questions for you

1. **Should the room editor and `/save` exist on the public deployment at all**, or only on the
   tailnet? My recommendation is tailnet-only. The answer decides how R0 is built.
2. **What should passing a test certify?** If it is "you read and engaged", the current
   evaluator plus light hardening is enough. If it is "you can do this in Claude Code", you need
   verifiable artifacts (e.g. output from a real `claude -p` run, a `SKILL.md` that parses), which
   is a bigger design change.
3. **Who is the audience now that it is public:** Kedash-internal trainees, or anyone? This
   affects the error-log IP retention, whether the TTS spend is worth it for anonymous visitors,
   and whether the corporate fiction still fits.
4. **Is the 3D office the product, or the wrapper?** One week of play telemetry (2D vs 3D
   completions; this needs a privacy-safe counter, not the error log) would settle whether R6–R8
   are worth funding, or whether 3D should be frozen at its current 16 chapters.
5. **How often will the content be re-verified?** Each pass so far has been reactive. A quarterly
   check tied to the Claude Code changelog, using the facts layer from R3, is my suggestion; it
   needs an owner.
6. **Grow chapters or deepen them?** Covering C5 by adding chapters needs R6 first; folding it
   into existing chapters doesn't.
7. **Videos:** produce them, or remove the "coming soon" placeholder from all 71 lessons?

## 7. Decisions (owner, 2026-11-25) and what they change

| # | Decision | Effect on the roadmap |
|---|---|---|
| 1 | Editor and `/save` are **tailnet-only** | R0: the Funnel-facing listener serves the game read-only (no `/save`). Simplest build: Funnel proxies to a second, read-only port bound to 127.0.0.1, and the existing 8888 listener stays for LAN/tailnet with the editor. Changing the Funnel target is an outward-facing change, so confirm before doing it. |
| 2 | Tests certify practice via **`claude -p` output or a `SKILL.md`** | R5 changes from "harden keywords" to **artifact grading**. The evaluator already has an `artifact` type (`skill`, `command`, `agent`, `settings`, `hook`, `mcp`, …; `engine/evaluator.js:72`). Add a `headless-run` kind that checks `--output-format json` structure (`session_id`, `result`, `total_cost_usd`, …) plus the nonce inside the prompt. Every chapter's practical needs re-authoring around one of the two artifacts. Caveat: a client-side grader can check shape, not that the run actually happened. |
| 3 | Audience is **anyone** | R0 must restrict `/tts` (allowlist of shipped lines, or cache-only). Stop storing IPs in `logs/errlog.jsonl`. Keep the Kedash fiction; it is clearly fictional. Lessons must not assume a corporate seat or plan. |
| 4 | **3D is the product** | R6 (layout as data), R7 (`play.js` split) and R8 (floor disposal) are funded, not conditional. R1 (bounds audit, slot fix) moves ahead of all content work. |
| 5 | Re-verify content **every month** | R3 (`data/facts.js`) becomes a prerequisite: monthly checks need a single place to change. Add a recurring check: a docs diff against the facts file plus the lessons whose `lastVerified` is older than 30 days. |
| 6 | **Deepen existing chapters** (no new ones) | R4 folds the missing features into existing chapters. **New constraint:** more lessons per chapter breaks 3D placement on floors 2–4 beyond ~4 lessons (P1), so R1/R6 must give each room capacity for ~8 lesson NPCs **before** R4 lands. |
| 7 | Videos: **YouTube hyperlinks where a relevant one exists, otherwise nothing** | `ui/lesson.js:32-35` renders `videos[]` as raw HTML and shows "coming soon" when empty. Change it to `{title, url, channel, published}` link cards and render nothing when the array is empty. Only link videos that match the *current* behaviour (official Anthropic channel preferred), and include them in the monthly check, because a stale video re-teaches stale facts. |

**Revised order:** R0 → R1 + R2 → R3 → R6 (room capacity) → R4 + content fixes (§4) → R5 (artifact grading) → video links → R7 / R8 / R9 incrementally.
